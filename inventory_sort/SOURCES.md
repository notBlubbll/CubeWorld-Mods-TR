# Local evidence for Inventory Sort

The basis is this machine's verified 2013 Alpha client, plus the project's pinned Qube Loader and CubeWorld-Reversal. The recovered source names may be wrong; everything was cross-checked against the actual instructions, and it is not treated as a complete vanilla source.

- Game SHA256: `84A7A132A84D4282338E7EA45A1940D32066D64E39CBAFED8F2418D5A6DC30BF`. PE timestamp `0x51EA955E`, SizeOfImage `0x3BC000`, entry RVA `0x28E1E0`.
- The SDK's `external/Qube-Loader/modloader/sdk/cube/items.hpp` defines the item types. `modloader/src/game/offsets.h` defines the inventory's outer vector at `Creature+0x11DC`, the `0x11C`-byte item cell, and the `0x118`-byte item body; the read limits keep 32 pages of 256 cells.
- `GameController+0x800954` is the player inventory Widget; `+0x800958` is the recipe Widget and `+0x80095C` the merchant inventory Widget. The recovered file `external/CubeWorld-Reversal/cube/control/GameController.cpp` records these pointers and modes 0 / 2 / 3 in its constructor section. The player Widget's `+0x160` points to the real inventory vector, `+0x164` to the owning controller, and `+0x194` to the mode.
- The recovered name of `0x4C2050` is `GameController::drawCurrencyPanel`; the actual function walks the inventory cells at `this+0x160` and draws icons, counts, prices, and the coins, writing the hover page/cell to `this+0x184/+0x188`. This module treats it as the InventoryWidget draw function; ECX is `this`, and `0x4C597A` is a `ret` with no argument stack.
- The drawing also reads the copper total at `items+0x128` and the platinum at `items+0x12C`. The view therefore includes the `0x130`-byte prefix starting at the original items, replacing only the first 12 bytes of the vector head and keeping the rest as-is.
- `0x4C6610` copies the hover cell to `+0x18C/+0x190` when a flag is set, then computes the selection box position; thiscall, `0x4C679E` is `ret 4`. Indices are converted before and after the call, so external code keeps reading real coordinates.
- `0x62DC20` gives the Widget's screen origin (outputs two floats, `ret 4`); `0x62F600` / `0x6291D0` return the width and height (x87 float, `ret`). The original drawing and the `0x4C6350` scroll computation both read the cell width/height at `+0x1A8/+0x1AC` and use `int((width-10)/(cellWidth+5))` and `int((height-40)/(cellHeight+5))`. The titles and sections reuse these formulas, with the origin offsets still x+10 and y+40; no fixed column or row count. The native scroll's current page row offset comes from the `+0x198` vector, and the maximum scroll range is at `+0x1A4`.
- Each title takes one row of the display copy, aligned to the original column count on the last row; these synthetic cells map to -1, and the real item bytes are preserved cell by cell. When the layout is first built, unused native empty slots are hidden; 0.1.6 remembers the category of displayed cells per the user's latest requirement — after a sale or pickup the slot is kept and the other cells do not shift forward. The same-session position record is shared by the drawing and the scroll view, isolated by controller/character/inventory base address; no blank is inserted into the real inventory. Titles always map to -1; when holding an item of the same tab, visible blanks point to verified real slots.
- `0x4C6350` is called not only from the draw entry but also by the native post-trade update path. 0.1.1 recomputes the scroll there using an independent temporary section view and restores the pointers afterwards; the last-draw snapshot used for click verification must not be refreshed, or a stale post-sale hover would be wrongly accepted. The helper functions and scroll disassembly are in `research/evidence/inventory-sort-sections-native-disassembly.txt`.
- Native detail nodes: `GameController+0x8008E4` is `preview` and `+0x8008EC` is `equippedpreview`; cross-checked against the constructor section `0x200239/0x20023B` and the native update section `0x48ED12..0x48F177`. A node's visible value is read from the current slot via `Node+0x3C -> state+0x68/0x94`. `Node+0x34` points to the Shape, `+0x40` to the Widget, and `+0x48` is the current 16-float transform matrix; `+0x38` is the local position state and must not be treated as the Widget.
- 0.1.3 tried to measure with `0x634A70` (recovered name `Node_transform_pair_to_screen`) but missed the local-to-screen transform. The user's new screenshot confirmed 0.1.3 was loaded and still occluding; the earlier offline tests had fed it screen rectangles directly and never covered that coordinate conversion. The old disassembly is kept in `research/evidence/inventory-tooltip-native-bounds-disassembly.txt`; that method is no longer used in 0.1.4.
- 0.1.4's live basis: with the user's authorization to keep a scroll hovered, `inventory-tooltip-0.1.3-failure-live.json` was captured read-only at 2026-10-25 10:30:36 +08:00 with the main detail visible. The `SmoothMeshShape` vtable's raw address is `0x71E92C` (after live relocation `0xE1E92C`); its vfuncs 6 (`0x669080`) / 7 (`0x669060`) return the Shape's local bounds at `+0x878/+0x87C` and `+0x880/+0x884`; the disassembly is in `inventory-tooltip-local-bounds-getters.txt`. These bounds already include the local animation position and must not add `Node+0x38` again.
- In the same record, the local bounds were about `(45.1754,-119.8242)..(353.1759,188.1758)`, the node matrix translation was `(793.8247,471.8243)`, and the converted screen frame was about `(839.0001,352.0001)..(1147.0006,660.0001)`. Yielding with the local box landed in an unrelated area; 0.1.4 transforms the four corners with the current column-major matrix, divides by the homogeneous w, takes the bounding box, rounds outward, and pads 3 more pixels. The current zoom and translation are supported; if the matrix, ranges, or a known Shape type cannot be verified, the titles hide for that frame. Only cached values are read; no new game function calls.
- `inventory-tooltip-0.1.4-schema-live.json` additionally verified that the comparison node uses the same SmoothMeshShape layout with a different current matrix; the comparison was hidden at capture time and it is used only as layout evidence. 0.1.4 logs once per visible node on the first valid screen-frame read, for relaunch checking — not every frame. The synthetic SDK replays the live case with the local boxes and independent node matrices, and requires that the counter-example omitting the translation really does produce occlusion.
- The loader draws ImGui in the tail of D3D9 EndScene, after the native details are already on screen. Swapping ImGui's own foreground/background lists cannot change their order relative to the native windows. 0.1.4 excludes the two detail rectangles (padded 3 pixels for the edges) from the titles' background, separators, text, and the empty-inventory hint, achieving detail-first through draw clipping; the native details are not redrawn and the cell coordinates do not change.
- 0.1.5's equipment-page fallback live case: `inventory-equipment-0.1.4-replay-live.json` recorded page 0 at 2026-10-25 10:50:14 +08:00 with 104 items, all count 1, all legal types — 12 chestplates, 10 gloves, 2 boots, 8 pauldrons, 69 weapons, 2 amulets, 1 ring. The player vtable, Widget ownership, mode 0, items base address, vector length, and capacity all passed the original preconditions. The full item bytes are kept in `inventory-equipment-0.1.4-cells.bin`, SHA256 `48106A183CB631FFC57AC9CAC9786FFBF3F04230848833C00894435BD87AF3F3`.
- That vector is `0x200AAAA8..0x200B1E08`, 29536 bytes. The first VirtualQuery region `0x200AA000..0x200B1000` is `PAGE_READWRITE`; the following `0x200B1000..0x200B3000` is `PAGE_EXECUTE_READWRITE`; both are readable, but the whole block crosses a boundary. The loader's `src/core/mem.cpp` `readable/regionContains` only accepts a single region, and `src/api/system.cpp`'s `apiMemRead` uses that check as-is. So the old whole-page read and the stale-input validation could both fail.
- 0.1.5 handles this limitation only inside this mod's read wrapper: the fast path of the whole-block success is kept, and when it fails across a 4 KiB page boundary, it slices at page boundaries and reads again through the same SDK. Windows VirtualQuery regions are page-aligned; each segment keeps the permission, readability, and range checks; any failure still falls back — no direct memcpy of game addresses, no changes to the loader or memory protection. The synthetic SDK enforces the same single-region rule at the live offsets and replays the full 104 equipment items, verifying the seven categories, 8 columns, the 192 display cells including titles/alignment, the full item bytes, and the tail-item correspondence.
- 0.1.6's pickup live case: `inventory-return-0.1.5-live.json` / `inventory-return-0.1.5-held-live.json` captured before and after the pickup. The equipment page has 105 real cells; after the pickup the held weapon is count 1, type 3; native slot 57 changed from a valid weapon to a real empty slot, and the page still has 89 empty slots. The old version re-compacted the sections, hid the original position, and only added one "put back" slot at the very end of the list; the row-end blanks still mapped to -1, so the user could not put back at a visible position.
- The native left-click path `0x47C54D..0x47C748` first checks the hover page/cell inside the real vector; the held item must match the page of the native `getItemTypeCategory` (`0x47FA30`), and the native swap/stack handles the rest. The recovered source `GameController.cpp` around lines 29547 and 30774 matches the pinned version. That category function returns 0 for 3..9, 23, 24; 2 for 11; 3 for 19/20; 1 otherwise; 0.1.6 only reuses this fixed mapping — no new game calls or hook points.
- The full held Cell sits at `Creature+0x11E8`, with the Item starting at `+0x11EC` — exactly +12 of the original items prefix. 0.1.6's click snapshot compares the whole `0x11C`-byte held record; swapping in an item of the same count still invalidates the old mapping. A real empty slot can have multiple display aliases; the reverse selection prefers the last actually-hovered display position, so the selection box does not jump to another alias. Aliases never create, copy, or write actual item cells.
- `0x47B450` returns the player's hover coordinates; the input paths of `0x47B600` and `0x47DDD0` contain the native pickup/place, equip, and trade operations. This module only checks the snapshot before input; it does not trade by itself and does not override input parameters or return values.
- At runtime it verifies the draw/selection entries, field accesses, return stack cleanup, and the mouse-input stack frame signatures. The disassembly is in `research/evidence/inventory-sort-native-disassembly.txt`.
- The potion hooks are `0x44AD30` and `0x4C76E0`, the lighting `0x448170`; the map and the explorer do not touch this module's five hook points. The potion price only matches the merchant's temporary inventory, and this module only changes the player Widget's display copy. The titles use the original loader's independent pass-through menu and do not intercept inventory mouse input. This is offline compatibility evidence; real combined use is still pending acceptance.

The shared loader, the launcher, and the original game files were not modified. The manager's install detection, independent switch, runtime lock, and removal backup follow the project process.
